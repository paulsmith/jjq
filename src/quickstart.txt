jjq — Local Merge Queue for jj

WHAT IT DOES
  jjq queues revisions and merges them to a trunk bookmark one at a
  time. Each merge is tested with a configurable check command. If the
  check passes, trunk advances. If it fails or conflicts, the item is
  marked failed and the queue continues.

CORE COMMANDS
  jjq init            Set up jjq one time (interactive without flags)
    --trunk NAME      Trunk bookmark (skip prompt)
    --check CMD       Check command (skip prompt)
    --strategy STR    Landing strategy: rebase (default) or merge
  jjq push REVSET     Queue a revision for merging
  jjq run             Process the next queue item
  jjq run --all       Process all queue items
  jjq run --all --jobs N  Check up to N merge candidates concurrently
  jjq status          Show queue, recent failures, and recently landed items
  jjq history ID      Show a submission's durable lifecycle history
  jjq history --change CHANGE_ID  Find all submissions for a change
  jjq check [--rev R] Pre-flight: test a revision without queuing it
  jjq requeue ID      Re-push a failed item back onto the queue
  jjq cancel ID       Cancel queued or running work cooperatively
  jjq tail            View check command output (follows by default)

AS AN AGENT
  Your job is to push finished work to the queue and wait for the verdict.
  You don't run the queue.
    jjq push @ && jjq wait <change-id>
  Run the wait as a background task so the queue drains while you work.
  wait exit codes: 0 = landed, 1 = rejected (reason and item ID on stdout),
  2 = unknown target or timed out. A bare check failure is pending, not a
  verdict — the item may be fixed and land later. After a landed verdict
  your working copy may sit on an obsolete revision: run
  jj workspace update-stale and start from trunk.

LANDING POLICY
  One squashed revision per unit of work: pushing more than one revision
  atop trunk is refused ("n revisions atop trunk; squash and re-push"),
  and pushing trunk itself is refused ("nothing to land atop trunk").
  A deliberate stack needs jjq push --allow-stack (recorded on the item,
  visible in status --json). Requeue re-runs the same gate.

UNFIXABLE FAILURES
  When an item cannot be fixed, record why:
    jjq reject <id> --reason "<diagnosis>"
  The reason reaches the submitter through status and wait (exit 1).
  Requeue or delete remains the human override for rejected items.

RESOLVING FAILURES
  If your push was marked failed (conflict or check failure):
    1. jj rebase -r <your-rev> -d <trunk-bookmark>
    2. Resolve any conflict markers in the affected files
    3. Verify: run the project's check command
    4. jjq push <your-rev>   Re-push (automatically clears the failed entry)
  Or, to retry without changes: jjq requeue <id>

AFTER A RUN LANDS ITEMS
  A jj workspace whose working copy sat on a landed change goes stale:
  every jj command there errors until you run, in that workspace:
    jj workspace update-stale
  If your jj commands suddenly fail after a merge, run this first.

THINGS TO KNOW
  - Push resolves a jj revset to one revision and queues it by change ID
  - Pushing your working-copy commit (@) moves the working copy to a new
    empty child, so edits after the push don't amend the queued commit
  - Queue is processed FIFO; each item gets a temporary workspace
  - A passing queue check creates a short-lived validation receipt; jjq
    rechecks its candidate, trunk, strategy, and check command before landing
  - If trunk or check configuration changes during a run, jjq requeues the
    unchanged item for a fresh check instead of landing stale work
  - `--jobs` defaults to 1; merge lookahead rechecks dependents after an
    earlier failure or tree change, while rebase currently remains serial
  - Re-pushing the same change ID replaces its queue/failed entry
  - Concurrent pushes are safe: they serialize on a metadata lock, so a
    push may wait briefly; it exits 3 only after a 15s timeout
  - The item being processed shows under "Running:" in status; it cannot
    be deleted or requeued while a runner is active
  - jjq run waits for an active runner, then drains what it left; only
    --no-wait exits 1 with "another queue runner is active"
  - jjq status --resolve <change> --json answers where a change stands:
    queued, running, failed, rejected, landed, or unknown (exit 10)
  - Files a check writes never land; the exact commit the check ran
    against is what lands
  - Cancel removes queued work immediately. Running checks stop as a process
    group; cancellation is not a failure and a landing CAS that already won
    remains landed
  - Use 'jjq check @' to test before pushing — catches conflicts early
  - Status shows recently landed items and conflicting file paths for failures
  - Failure output shows concrete jj commands with your actual change IDs
  - Exit codes: 0=success, 1=conflict/failure, 2=partial, 3=lock held, 10=usage error

TROUBLESHOOTING
  jjq doctor           Validate config, bookmarks, locks
  jjq requeue ID       Re-push a failed item (runs pre-flight conflict check)
  jjq delete ID        Remove item from queue or failed list
  jjq clean            Remove orphaned jjq workspaces
